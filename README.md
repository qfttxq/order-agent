# order-agent

把一段客户需求，变成五份能直接用的东西：**类型判定、匹配度、澄清清单、三档报价、验收单草稿**。

给自由开发者 / 小工作室用的接单前评估工具。输入是客户在微信或平台上发来的一段话，输出是一份可以立刻拿去沟通的报告。

```
$ order-agent analyze "我们有 300 份产品手册，客服每次都要翻半天，想做个能直接问的。预算 3 万。"

# 需求评估：知识库 / RAG

> **值得谈，但先谈预算。** 客户预算 ¥30,000 低于「标准版」下限 ¥38,000，
> 先缩范围或分期，别直接降价。

## 一、判定
| 项目 | 结果 |
|---|---|
| 类型 | 知识库 / RAG |
| 置信度 | 95% |
| 匹配度 | 高，值得优先投入 |

**判定依据**（引号内为客户原话）
- 有现成文档语料：「我们有 300 份产品手册和培训材料，客服每次遇到客户问…」
- 有明确的问答/查资料场景：「…料，客服每次遇到客户问参数都要翻半天，想做个能直接问的」
- 关注答案准确性：「要求答案准确，最好能给出处」
```

## 为什么它是个 Agent，不是一段脚本

普通的报价脚本是「输入数字 → 套公式 → 出价格」。这个工具要做的是先**读懂需求**，再决定用哪个公式：

- 同一个「300」，在知识库需求里是**文档份数**，在自动化需求里是**每日订单量**，对应两套完全不同的计价逻辑
- 「对方没有接口」和「要求对接接口」用的是同一个词，意思正好相反，判反了报价直接错一个量级
- 「知识库 + 顺便自动同步文档」是知识库项目，不是工作流项目——判错会让报价从 3.8 万跳到 8 万

这五份产出是**一条链**：类型决定问什么、问什么决定报价基准、报价决定验收标准。任一环节判错，后面全部错位。所以它不是五个独立功能，是一条判断链。

## 快速开始

```bash
cd order-agent
export PYTHONPATH=src

# 分析一条需求
python -m order_agent analyze "需求文本"
python -m order_agent analyze -f req.txt --budget 30000 --channel 程序员客栈

# 输出结构化 JSON（接其他系统用）
python -m order_agent analyze "..." --json

# 批量跑样本
python -m order_agent batch -f samples/requirements.jsonl

# 评测
python eval/run_eval.py --no-llm     # 纯规则，完全确定
python eval/run_eval.py              # 规则 + 模型交叉验证
```

零第三方依赖，Python 3.10+ 即可运行。模型校验是可选的，没配 API Key 也能完整工作。

## 三个关键设计

### 一、结论由规则给，模型只做第二意见

这不是保守，是被现实逼的。让模型直接输出「这是 K 类，报价 2 万」有三个具体问题：

1. **不可复现**——同一段需求今天判 K、明天判 A，你没法向客户解释
2. **不可评测**——每次测出来的准确率都不同，指标没有意义
3. **不可兜底**——模型挂了、余额没了、网络断了，工具就完全不能用了

所以流程是：规则先出结论 → 模型独立判一次 → 两者不一致时标注冲突，交给人看。

冲突本身是有价值的信息。实测样本 `b08`：

> 「销售去见客户前要准备资料，竞品参数、报价、案例都得现找，想让系统根据客户行业自动推相关的材料给他。」

规则判 A（命中「自动」，但没有出现「知识库/检索」这类词），模型判 K（80%，"属于知识库检索增强"）。系统标了 `conflict: true` 并提示人工复核。

这类需求靠关键词救不回来——它要的是**语义理解**。模型在这里补的正是这个缺口，但它的输出不能直接当结论，因为下一次它可能给出别的答案。

### 二、澄清清单按缺口生成，说过的不再问

清单不是固定问卷。每条问题带一个 `gap` 字段，指向一个信号名；该信号已命中，这条问题就**整个消失**——不是标成「可不答」，是不出现。

客户说「不同部门只能看自己组的资料」，再问一句「能看的资料一样吗」，示范效果是负的。

同时每条问题带「为什么问」。客户看到解释更愿意回答，这直接决定澄清环节能不能拿到信息。

### 三、验收项必须能被第三方独立判定

私下收款没有平台兜底，唯一的保护就是「什么叫做完」写没写清楚。

所以「效果好」「响应快」「准确率高」这类词一律不进验收单，全部换成可判定的表述：

| 类型 | 验收项示例 |
|---|---|
| 知识库 | 随机抽 30 条回答，全部能对应到原文片段，**任一条出现编造即视为该项不通过** |
| Agent | 连续执行 100 次，**成功完成 ≥ 95 次**；「失败」不含上游系统不可用、权限失效、源数据缺失 |

A 类刻意不写「准确率」——准确率取决于客户系统稳不稳定、流程标不标准，写进合同等于承担无限责任。改成「成功率 + 异常可接管 + 分阶段验收」。

## 评测

三批独立样本，共 32 条。写法参照平台需求的真实风格（口语、省略、带错别字），但内容由我编写——**不是真实订单数据**。

| 样本集 | 用途 | 类型判定 | 必问覆盖 | 平均问题数 |
|---|---|---|---|---|
| `requirements.jsonl`（13 条） | 开发集，调规则用 | 13/13 | 87% | 11.2 |
| `requirements_holdout.jsonl`（9 条） | 留出集，第一轮不调规则 | 9/9 | 92% | 11.8 |
| `requirements_blind.jsonl`（10 条） | 盲测集，只在最后跑一次 | **9/10** | 85% | 12.1 |

**这些数字该怎么读，得说清楚：**

1. **100% 那两批不能当结论。** 规则是照着开发集调的，在同一批样本上评测必然好看。留出集第一轮跑出 7/9，暴露了两个真 bug（「两万条」中文数量没解析、「没有接口」被当成「要求对接」）；修完变成 9/9，但这批样本也被「看过」了，所以同样偏乐观。

2. **盲测集 9/10 更接近真实水平。** 剩下的 1 条就是上面说的 `b08`——需要语义理解才能判对，是规则方法的固有上限。真实派单上预计在 **75%–90%** 之间，需要用实际接到的需求持续校正。

3. **必问覆盖度只测「问没问到」，不测「客户答不答」。** 真实场景里客户可能跳过一半问题，那部分损失这个指标反映不出来。

4. **报价落位区间是按我自己的定价策略划的**，不是市场公允价。它验证的是「公式有没有算错」，不是「客户会不会接受这个价」。

复现：

```bash
python eval/run_eval.py --no-llm --samples requirements_blind.jsonl --out eval-blind.md
```

## 已知局限

- **强依赖中文关键词命中。** 换一种说法（「内部百度」「智能助手」）能命中，但完全绕开关键词（「资料太散」）就会退化到「信息不足」。这正是需要模型兜底的地方。
- **否定句只处理了「不/没/无/未」这类常见形式。** 「并非没有接口」这种双重否定会判错。
- **流程条数无法自动抽取。** A 类报价目前按系统对接数推算，准确做法是靠澄清清单问出来，所以第一次报价只能给区间。
- **报价区间是自定价策略**，市场验证要靠实际成交反馈调整。

```

├─ src/order_agent/
│  ├─ signals.py      # 信号抽取：文档量、系统、拒绝信号、否定检测
```

## 测试

```bash
python -m pytest -q     # 62 passed
```

测试覆盖的不是「函数能不能跑」，而是真实踩过的坑：

- `test_negated_integration_is_not_integration` — 「厂商不给接口」判反了结论会完全反
- `test_kb_declared_beats_attached_automation` — 「知识库 + 自动同步」判成 A 类，报价从 3.8 万跳到 8 万
- `test_excel_is_not_business_system` — Excel 算成业务系统，会把数据处理单判成 Agent 单
- `test_known_doc_count_is_not_asked_again` — 已经说了 300 份还问「一共多少份」
- `test_verdict_reasons_quote_different_fragments` — 三条依据引用同一句话，客户一眼看出是模板
- `test_rejected_brief_has_no_acceptance_sheet` — 写着「不建议报价」，下面却列着「Recall@5 ≥ 0.85」
- `test_unknown_doc_count_is_marked_provisional` — 客户没说多少份，报告却写「按语料规模估算：50 份」，把假设说成事实
- `test_onprem_raises_days_not_only_price` — 私有化价格 ×1.4、工期一天不加，报价单自相矛盾
- `test_gbk_file_analyzes_end_to_end` — 记事本存成 ANSI 的需求文件直接崩栈，这是最高频的真实输入
- `test_null_content_returns_none` — 模型返回 `content: null` 时崩 TypeError，与「绝不抛出」的承诺相反
